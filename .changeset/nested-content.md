Schema fields for nested content.

`NodeSpec` gains `content` as a content expression (`'block+'`, `'listItem+'`, `'paragraph block*'`: node and group names, sequence, `|`, parentheses, `* + ? {n} {n,} {n,m}`), `group` (default `block` or `inline`; a node that sets it is only in the groups it lists), `marks` (`'_'` all, `''` none, or mark names) and `isolating`. `'inline'` and `'text'` stay as aliases of `inline*` and `text*` (the latter with no marks). The registry compiles every expression once and exposes `isTextblock(type)`, `contentMatch(type)` and `createAndFill(type, data?)` (through `tr.registry`). An unknown name in an expression, or a node that can never be created, throws at editor creation and names the plugin.

**Breaking:** an omitted `content` on a non-atom block now means inline content only (a textblock). A block that holds other blocks must declare `content: 'block+'` (or a narrower expression).

Normalization follows the schema at every depth: children that do not match their parent's content are fixed in order (an inline run is wrapped into a textblock, missing nodes are filled in before a node or at the end, a node is wrapped into the containers it needs, e.g. a paragraph in a list into a list item, a block that fits nowhere is unwrapped, an atom block is hoisted out). An empty container is filled (an empty list gets a list item with an empty paragraph) and never gets a text. Marks and inline nodes a textblock does not allow (`marks`, its content) are removed. Unknown types still count as fitting and are never changed. The content check runs on the nodes a transaction touched (everything on load).

HTML parse places content through the schema: an element a plugin claims that is not a textblock (a container such as a quote or a list) keeps its nested blocks, and its inline runs go into the textblock its content expects (`<li>text</li>` becomes a list item holding a paragraph; loose text in a list becomes its own item). Unclaimed `ul`, `ol`, `li`, `blockquote` and table tags are still unwrapped. Pasted JSON gets the same wrapping at every depth. `nodeText` and the clipboard text flavor put `\n` between adjacent blocks at every depth, so a list or a quote reads as lines.

Structural transforms on `Transaction`: `tr.wrap(type, data?, range?)` wraps the blocks of each range into `type` (adding inner wrappers such as a list item), `tr.lift(range?)` moves them out of their container (splitting it, removing it when left empty), `tr.setBlockType(type, data?, range?)` changes textblocks to another textblock type (marks it does not allow are removed), `tr.split(point, depth?, typesAfter?)` splits a textblock and its ancestors, and `tr.join(path)` joins a node into a compatible previous sibling (two lists). Each checks the schema first: it produces a valid document or changes nothing and returns false (null for `split`). New core commands `wrapIn(type, data?)`, `lift()` and `setBlockType(type, data?)` work at every selection range and answer `can()`.

Range delete works across depths: nodes covered whole at any depth are removed, the end textblock's content joins the start textblock across different parents (when the start textblock allows it), containers left empty are removed (or refilled when their parent needs them), and the containers cut open get what their content lacks. Isolating nodes are never merged or removed by a range that only partly covers them: a range across table cells empties the covered text in each cell and keeps every cell. The result is valid without normalization.

Backspace, Delete and Enter at container edges: Backspace at the start of a container's first textblock lifts it out (a paragraph at the start of a quote), when the lift is valid; otherwise it joins into the last textblock before (searching into a previous container) and selects an opaque node first, as before. Delete mirrors it. Neither crosses an isolating node: at a cell's edge nothing happens, and next to a table an empty paragraph is removed and the caret goes to the end of the last cell (the start of the first one for Delete), while a non-empty one only moves the caret there. Enter in an empty textblock inside a container lifts it out when valid (else it splits as before); when the parent does not allow the new block's type after the split, the new block takes the textblock type the parent expects there. Tab has no core binding. `insertBlockNode` and `replaceSelectedNode` place nodes through the content match: a block the caret's parent does not accept goes to the nearest ancestor that does (splitting the ancestors at the caret), else it is wrapped (`findWrapping`: a list item inserted in a paragraph becomes a list), else nothing happens (a selected range is not deleted either). An empty paragraph a container must keep (the first one in a list item) gets the node after it, inside the container. Every block the core creates next to a node (after a split, a removed node, IME replacing a node) is `createAndFill` of the default type of its position; in a flat document that is still the default block.

`editor.isActive(type, data?)` is true when the block at a range's start or any container around it is `type` (a caret in a list item's paragraph is active for `bulletList`, `listItem` and `paragraph`); `data` is checked against the innermost node of that type. Marks are unchanged.

Slices for copy and paste: a new public type `Slice = { content, openStart, openEnd }` (the content of a range below the deepest node holding both ends, and how many block levels are cut open at each end), with `tr.getSlice(range?)` and `tr.insertSlice(slice, range?)`. `insertSlice` fits the slice at each range: an open end merges into the caret's textblock when its open nodes line up with the caret's ancestors (two list items pasted into a list item's paragraph give two items in that list), whole nodes go where the content match accepts them, wrapped when needed (list items pasted into a root paragraph become a list, table cells a table) or unwrapped one level; the result is valid or nothing changes (false). `insertFragment(fragment)` is `insertSlice` with a fragment's open depths (an edge textblock merges, other edges go in whole), so flat documents behave as before; containers are now fitted instead of pasted as siblings. The core paste and drop use slices: `transformPasted` still gets and returns a `Fragment` (the slice's content) and the open depths are clamped to what it returns. The `application/x-penline-fragment` JSON carries the slice with its open depths (a plain fragment array when they are a fragment's, as before; old array payloads paste as before), and the HTML flavor wraps blocks the root does not accept in their ancestors (two `<li>` go out inside their `<ul>`). Pasted HTML is open as far as its content allows (never into a table cell), so a pasted list merges into the list around the caret; an open end that does not line up with the caret's ancestors is closed, so a lone container (a quote, a list, a table) pasted into a root paragraph goes in whole; whole list items (an old payload, `insertFragment`) pasted into a list item become items of that list, never a list nested in the item. `insertInlineNode` skips textblocks whose content does not allow the node (`registry.allowsInline`), not only `content: 'text'` ones.
